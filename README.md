# HiP-VesselAdapt

**Paper title:** Spacing-Aware Parameter-Efficient Adaptation of Frozen 3D
Foundation Models for Multi-Resolution HiP-CT Vessel Segmentation
(`HiP-VesselAdapt` is this codebase's short name.)

A lightweight, physics-aware adapter for **SAM-Med3D** (a pretrained 3D foundation
segmentation model), fine-tuned to segment blood vessels in high-resolution
synchrotron tomography (HiP-CT) scans of human organs (Heart, Lung, Kidney), each
scanned at a different physical voxel spacing.

**Status: work in progress.** The numbers in this README are real, from
actually-executed runs — not fabricated or rounded up. They are also, honestly,
still low in absolute terms (see "Known Limitations"). This document exists to
give an accurate picture of what works, what's verified, and what's still open.

---

## 1. What this project actually does

- Takes a **frozen, pretrained 3D foundation model** (SAM-Med3D, ViT-based image
  encoder + promptable mask decoder) and adapts it to a new imaging domain
  (ex-vivo synchrotron CT) using a small, trainable **Physics-Aware Adapter**
  that conditions on each scan's real voxel spacing (in micrometers).
- Trains **one joint model** across three organs with three different physical
  resolutions (Heart 26.04μm, Lung 169.36μm, Kidney 50μm), rather than one model
  per organ.
- Evaluates with Dice, Hausdorff Distance (HD95), and Betti numbers (topological
  correctness — connected components and independent loops).

## 2. Data

Source: ESRF Human Organ Atlas (HiP-CT), raw `.jp2` slice stacks, downloaded and
placed under `data/raw/<organ>_jp2/`.

**Important caveat:** these raw downloads ship as grayscale tomography volumes
only — **there is no expert vessel annotation included.** All "ground truth"
masks in this project are **weak pseudo-labels** generated by a multiscale
Frangi (Hessian-based) vesselness filter (`utils/pseudo_labels.py`), not human
annotations. This is stated explicitly here because it materially affects how
every Dice/HD95/Betti number in this document should be interpreted: they
measure agreement with a heuristic label, not clinical ground truth.

### 2.1 Real ground truth added: SenNet+HOA kidney dataset (new, not yet integrated into training)

To address the pseudo-label limitation above, real expert-annotated vessel
masks were obtained from the Kaggle **SenNet + HOA "Hacking the Human
Vasculature in 3D"** competition (`data/blood-vessel-segmentation.zip`, 21GB
compressed / 43.5GB uncompressed, 14,365 files) — verified directly (label
TIFFs contain only values `{0, 255}`, and real foreground vessel fractions of
0.29%–1.54% were measured across sample slices from 3 different kidneys, not
empty or synthetic).

Voxel spacing is **not** embedded in the TIFF files (checked: `XResolution`/
`YResolution` tags are dummy placeholder values) and is not shipped as a
metadata file in the zip. Every spacing value used in this project is taken
from the dataset's official companion paper — Nature Methods,
["Vasculature segmentation in 3D hierarchical phase-contrast tomography images of human kidneys"](https://pmc.ncbi.nlm.nih.gov/articles/PMC13470036/),
Table 1 — and recorded, with source citation, in
`data/kidney_metadata_verified.csv` (generated by
`utils/kidney_metadata_verification.py`):

**Notable, unplanned finding:** `kidney_1_dense` and `kidney_1_voi` are the
**same physical specimen** at two real, distinct resolutions (50.00μm vs.
5.20μm, ~10x apart), both with real dense expert annotation. This is a genuine
(if limited — one specimen, two resolutions) same-organ multi-resolution pair,
usable for a real resolution-generalization test: train on the ~50μm kidneys,
evaluate on the held-out 5.2μm `kidney_1_voi` as a genuinely unseen resolution
— without resorting to synthetic downsampling.

**Data pipeline integrated (2025-09-13):** `utils/convert_kidney_gt_to_memmap.py`
converts all 5 real-GT train samples (kidney_1_dense, kidney_1_voi, kidney_2,
kidney_3_dense, kidney_3_sparse — ~45GB memmap total) directly from the zip
(no intermediate raw-extract step; Python's `zipfile` supports efficient random
access unlike gzip streams). `utils/real_gt_dataset.py` (`RealGTKidneyDataset`)
loads these as a **separate, configurable dataset mode** — the existing
Frangi-pseudo-labeled `MultiOrganHiPCTDataset` pipeline for Heart/Lung/Kidney
is untouched.

Verified via `diagnose_real_gt_dataset.py` (data pipeline only, no training):
shapes match, spacing is correct per sample, and masks are strictly binary.
A foreground patch was also visually inspected during development (ad hoc,
not part of the committed code — this project's diagnostic scripts print
numeric statistics only, no image files) and confirmed the real GT precisely
traces an actual vessel cross-section and tissue boundary visible in the raw
image, unlike the noisier Frangi pseudo-labels used elsewhere in this project.

**Real-GT baselines trained and evaluated (2025-09-13)** — see section 5.2 for
full numbers. `evaluate_real_gt.py` (Dice/IoU/clDice/HD95/ASSD, separate from
`evaluate.py` which targets the pseudo-labeled organs) and `train_real_gt.py`
(resumable, checkpoints every epoch, `checkpoints_real_gt/`) run against
`RealGTKidneyDataset`. `kidney_1_voi` (the 5.2μm specimen) is excluded from
training by default in `train_real_gt.py` to keep it genuinely held out for
the planned same-specimen resolution-generalization test.

**A real bug was found and fixed in `evaluate_real_gt.py` itself** while
building this: `soft_cldice.forward(y_true, y_pred)` (from
`external/clDice/cldice_loss/pytorch/cldice.py`) returns `1 - clDice` (a
**loss**, same convention as `soft_dice()` in the same file), not the raw
clDice score. The first run reported clDice≈0.97 alongside Dice≈0.03, which
is inconsistent almost by construction — that number was the *loss*, not the
score. Fixed to `1.0 - cldice_fn(targets, binary_pred).item()`; corrected
scores now sit in the same range as Dice, as they should
(`losses/combined_loss.py`'s use of this same function as a *training* loss
term was already correct and unaffected).

**Also found:** real kidney vasculature is sparse enough that random 64³
patches miss it entirely most of the time (measured: 71-80 of 100 random
patches had zero annotated foreground). Dice/IoU/clDice/HD95/ASSD are
mathematically undefined or misleadingly favorable on an empty target, so
`evaluate_real_gt.py` and `train_real_gt.py` both explicitly skip/exclude
empty-target patches from metric averaging and gradient steps respectively,
and report the exclusion count rather than hiding it.

**Not yet done:** Plain LoRA is implemented (`models/lora.py`,
`models/plain_lora_model.py`) and loads/runs correctly, but has not yet been
trained or evaluated against real GT (time-constrained — see section 7). The
same-specimen resolution-generalization test, Spacing-Conditioned LoRA, and
ablation study also remain.

## 3. Pipeline architecture

```
data/raw/<organ>_jp2/*.jp2          (raw ESRF download)
        |
utils/convert_to_memmap.py          -> data/memmap/<organ>.dat (raw np.memmap)
        |                               (NOT .nii.gz -- see "Why memmap" below)
utils/dataset.py (MultiOrganHiPCTDataset)
        |  - grid-aligned random patch sampling (64^3 default)
        |  - Frangi pseudo-label generation, cached per grid block
        |  - z-score normalization
        v
models/hip_vessel_model.py (HiPVesselAdaptModel)
        |  - SAM-Med3D image_encoder (frozen, pretrained, torch.no_grad())
        |  - models/physics_adapter.py: PhysicsAwareAdapter (trainable)
        |  - SAM-Med3D prompt_encoder (auto-prompted, see below)
        |  - SAM-Med3D mask_decoder (trainable)
        |  - models/collapse_head.py: CollapseDetectionHead (trainable, untrained/unvalidated so far)
        v
losses/combined_loss.py (HiPVesselLoss)
        |  - Soft Dice + clDice (topology) + anisotropic gradient penalty
        |  - + class-weighted BCE-on-logits (see "Known bugs fixed" below)
        v
train.py  (resumable, checkpoints every epoch)  ->  checkpoints/best_model.pth
evaluate.py            -> Dice / HD95 per organ
evaluate_topology.py   -> Betti numbers (b0, b1) per organ
baseline_zeroshot.py   -> same metrics with NO fine-tuning, for comparison
```

### Why `np.memmap` instead of `.nii.gz`?

`.nii.gz` is gzip-compressed, and neither SimpleITK nor ITK can randomly seek
into a compressed stream — every patch read re-decompresses from the start of
the file. Measured cost: **15–56 seconds to extract a single 64³ patch**, which
makes training infeasible. `utils/convert_to_memmap.py` converts each organ's
raw slice stack directly to an uncompressed flat binary array once
(RAM-safe: one 2D slice at a time), after which patch extraction is
effectively instant.

### Why an "auto-prompt" for SAM-Med3D's decoder?

SAM-Med3D's `mask_decoder` is a **promptable** head (point/box), not an
automatic dense-segmentation head. Called with no prompt at all
(`points=None, boxes=None`), it has no spatial cue and — verified empirically —
saturates to predicting **every voxel as foreground** after training. We
auto-prompt with two corner points spanning the whole volume (standing in for a
whole-volume box; SAM-Med3D's own box-embedding code has a hardcoded 2D-only
reshape that crashes on this 3D port, so the equivalent intent is expressed via
points instead — see comments in `models/hip_vessel_model.py`).

## 4. Real bugs found and fixed in this project (chronological)

Each of these was diagnosed by actually running code and reading real output,
not guessed:

1. **No real ground truth.** Original pipeline compared predictions against a
   threshold of the *same input image* (`targets = (images > mean+0.5*std)`).
   Replaced with Frangi pseudo-labels.
2. **Wrong vessel polarity.** Frangi's `black_ridges` defaulted to `False`
   (vessels assumed brighter than tissue). Visual inspection showed vessels are
   *darker* (a clean airway/vessel cross-section in the lung scan was only
   traced correctly with `black_ridges=True`) — fixed for all 3 organs.
3. **I/O bottleneck.** See "Why np.memmap" above.
4. **Untrained "foundation" backbone.** `checkpoint_path` defaulted to `None`
   everywhere, so the frozen backbone was frozen *random* weights — the adapter
   was learning on top of noise. Downloaded the real SAM-Med3D checkpoint
   (`external/SAM-Med3D/ckpt/sam_med3d.pth`, 1.2GB) and fixed the loading code:
   the release checkpoint is a full training-state dict
   (`model_state_dict` key, not a raw state dict), and requires the
   `vit_b_ori` architecture variant (768-dim, 128³ pretraining), not the
   registry's default `vit_b` (384-dim, 256³) — loads with 0 missing/unexpected
   keys once corrected.
5. **Decoder collapse to all-foreground.** See "auto-prompt" above. Root cause:
   sigmoid saturation + no prompt + weak sparse-target gradient signal. Fixed
   with the auto-prompt *and* a class-weighted `BCEWithLogitsLoss` term
   (computed on raw logits, numerically stable even at saturation — plain
   probability-space Dice/clDice cannot recover once sigmoid saturates).
6. **Fragile long training runs.** This machine is a shared desktop (not a
   dedicated GPU box) with heavy Chrome usage competing for its ~15GB RAM;
   background training jobs get OOM-killed unpredictably. `train.py` now
   checkpoints **every epoch** (not just at the end) and supports
   `resume=True`, so a kill costs at most one epoch of progress instead of the
   whole run.
7. **Three separate bugs surfaced moving the 100-epoch run to a Kaggle GPU
   kernel** (local CPU-only hardware can't finish 100 epochs × 2 models in
   reasonable time, so the controlled retrain moved to Kaggle's free GPU
   tier), each diagnosed from the kernel's actual stderr log, not guessed:
   - **Input-path detection.** Kaggle mounts datasets/competitions under
     `/kaggle/input/datasets/<owner>/<name>/` and
     `/kaggle/input/competitions/<slug>/`, not flat under `/kaggle/input/` —
     the kernel script's original flat-path assumption found nothing. Fixed
     with a bounded recursive search (`find_by_marker()`) for a directory
     containing a known marker file/subfolder instead of a hardcoded path.
   - **Working-directory disk quota.** Materializing kidney_1_dense +
     kidney_1_voi as `np.memmap` copies needs ~23GB; `/kaggle/working`'s
     quota is much smaller and the conversion step filled it mid-run
     (`Bus error`, `No space left on device`). Fixed by adding a
     `raw_tiff_root` mode to `RealGTKidneyDataset` that reads TIFF slices
     directly from the read-only competition mount per `__getitem__` call,
     skipping memmap conversion entirely — the mount doesn't count against
     the working-directory quota.
   - **clDice import.** `external/clDice/cldice_loss/pytorch/cldice.py`
     (upstream, freshly `git clone`d by the kernel each run) does
     `from .soft_skeleton import SoftSkeletonize`, a package-relative import
     that only resolves when the file is imported as part of an actual
     Python package. This project loads it as a standalone file with no
     parent package, which always fails that form regardless of platform —
     it happened to go unnoticed locally only because an earlier,
     uncommitted local edit to this vendored file had added a
     `try/except ImportError` fallback that the fresh Kaggle clone doesn't
     have. Fixed in `utils/load_cldice.py`: `soft_skeleton.py` is loaded and
     registered in `sys.modules` first, then `cldice.py`'s source is read
     and its relative-import line is rewritten to a plain absolute import
     before the module is executed, so it works whether or not upstream
     ever adds the fallback itself.
8. **SAM-Med3D backbone silently reported "not importable" on Kaggle.**
   `external/SAM-Med3D/segment_anything/__init__.py` does `from utils import
   *` — an absolute (not package-relative) import intended to reach
   SAM-Med3D's own `external/SAM-Med3D/utils/` package, which only works
   correctly when SAM-Med3D's repo root is the first thing on `sys.path`
   that defines a top-level `utils` name. This project also ships its own
   top-level `utils/` package, and the model files previously did
   `sys.path.append(sam_med3d_path)` (appending, so this project's own
   `utils/` package — already earlier on `sys.path` — wins the name
   collision) inside a bare `except ImportError: HAS_SAM_MED3D = False`,
   which silently swallowed whatever the real underlying error was. Fixed
   with `utils/load_sam_med3d.py`: `sam_med3d_path` is inserted at the front
   of `sys.path` only for the duration of the `segment_anything` import, and
   any `utils`/`utils.*` entries `sys.modules` picked up during it are
   evicted afterward so this project's own `from utils.xxx import yyy`
   calls elsewhere keep resolving against this project's real `utils/`
   package. The bare `except ImportError` swallow was also removed so any
   future backbone-import failure surfaces its real traceback instead of a
   generic "not importable" message.
9. **CUDA "no kernel image is available for execution on the device."**
   With the previous two bugs fixed, the kernel reached actual training —
   and immediately hit a hardware/software mismatch: Kaggle had assigned a
   Tesla P100 GPU (compute capability `sm_60`), which the pre-installed
   PyTorch build on the kernel's Docker image doesn't support (`sm_70`
   minimum). `kernel-metadata.json` didn't request a specific accelerator,
   so Kaggle picked whatever was available from its pool. Fixed by setting
   `"machine_shape": "NvidiaTeslaT4"` in `kernel-metadata.json` (`sm_75`,
   within the supported range).
10. **`RuntimeError: The size of tensor a (4) must match the size of tensor
    b (8)` in SAM-Med3D's image encoder.** With a working GPU, training
    reached the model's first real forward pass and crashed adding a
    128³-pretraining-sized positional embedding (8 tokens/axis at patch 16)
    to this project's 64³-patch input (4 tokens/axis). The fix for this —
    interpolating `pos_embed` (and, in `mask_decoder3D.py`, the dense/image
    prompt embeddings) to the actual input size when it doesn't match the
    pretrained size — had only ever been applied as an uncommitted local
    edit to the vendored `external/SAM-Med3D` checkout, so it silently
    vanished whenever that repo was freshly `git clone`d (as the Kaggle
    kernel does every run). Same root pattern as bug 7's clDice issue.
    Fixed properly this time: the patch is now `utils/patch_external_repos.py`,
    an idempotent, self-checking text patch (fails loudly if upstream's
    source no longer matches what it expects, rather than silently doing
    nothing) applied right after every fresh clone, locally or on Kaggle.

### 5.2 Real-GT kidney baselines (SenNet+HOA, no pseudo-labels involved)

Literal output of `evaluate_real_gt.py`, run against real expert-annotated
vessel masks (see section 2.1) — `kidney_1_dense`, `kidney_2`,
`kidney_3_dense`, `kidney_3_sparse` (100 random 64³ patches sampled per run;
71-79 excluded as empty-target — see note above), on CPU. `kidney_1_voi` is
held out from all training here, reserved for the planned resolution-OOD test.

**Terminology correction:** none of these are "full" (whole-backbone)
fine-tuning — the SAM-Med3D image encoder is frozen in every row, including
zero-shot. The only variables are (a) whether a trainable adapter sits after
the frozen encoder (PhysicsAwareAdapter) or trainable low-rank updates sit
inside the encoder's attention layers (LoRA), and (b) the always-trainable
mask_decoder. An earlier version of this README and `train_real_gt.py`'s
docstring called this "full fine-tuning," which was inaccurate; corrected here.

| Model | Trainable | Trainable component | Dice | IoU | clDice | HD95 (voxels) | ASSD (voxels) |
|---|---|---|---|---|---|---|---|
| Zero-shot SAM-Med3D | 0% | none (no training) | 0.088 | 0.052 | 0.076 | 48.1 | 25.2 |
| PhysicsAwareAdapter (10 epochs) | 7.65% | adapter + decoder | 0.157 | 0.094 | 0.139 | 36.2 | inf* |
| Plain LoRA, r=4 (10 epochs) | 7.75% | LoRA (24 attn layers) + decoder | 0.067 | 0.038 | 0.057 | 45.7 | 24.8 |
| **Spacing-Conditioned LoRA, r=4 (10 epochs)** | **8.88%** | spacing-modulated LoRA + decoder | **0.206** | **0.131** | **0.261** | **23.4** | inf* |

**In-distribution, Spacing-Conditioned LoRA beats every other model on every
metric** — including Plain LoRA (its most direct ablation: identical
architecture and training protocol, the *only* difference is whether the
LoRA branch is modulated by real physical voxel spacing). Trainable overhead
is modest (8.88% vs. 7.65-7.75%).

**⚠️ This does NOT hold out-of-distribution — see section 5.3, which reverses
this ranking.** The in-distribution result above should not be read as the
project's conclusion on its own.

**Honest, not-hoped-for finding (Plain LoRA):** Plain LoRA (10 epochs)
underperforms even the untrained zero-shot baseline, and is well below both
adapter-based methods. Reported exactly as measured — no cherry-picking.
Plausible explanations, none yet confirmed:
- LoRA (rank 4) modifies attention *inside* the frozen encoder; the adapter
  modifies the encoder's *output* feature map directly, right before the
  decoder consumes it — a shorter, possibly easier optimization path for the
  same number of gradient steps (~170-220 in each case).
- All three trained runs used identical loss weights and learning rate
  (tuned originally against PhysicsAwareAdapter) — never re-tuned per
  architecture, a real confound. That Spacing-Conditioned LoRA *still* won
  despite this is encouraging, but a proper sweep hasn't been done.
- 10 epochs / ~20 real (non-empty) gradient steps per epoch may simply be too
  few for Plain LoRA specifically to move the frozen encoder's behavior
  enough to matter, given it's several layers removed from the loss — yet
  Spacing-Conditioned LoRA, with the same LoRA mechanism plus spacing
  modulation, converged to a much lower loss (1.56 vs. Plain LoRA's 2.05)
  under the identical protocol, suggesting the spacing conditioning itself
  (not just "more LoRA training") is what made the difference.

This needs more investigation (more epochs, a per-architecture learning rate
sweep, multiple seeds) before treating the ranking above as final — but
these are the real, current, unqualified results, reported as measured.

\* **ASSD=inf for PhysicsAwareAdapter and Spacing-Conditioned LoRA, reported
honestly rather than hidden or omitted:** a MONAI warning ("the prediction of
class 0 is all 0") indicates at least one evaluated patch had a completely
empty *prediction* (surface distance is undefined when one side has no
surface at all). Plain LoRA's ASSD did not hit this (24.8, finite) on the
identical evaluation protocol — worth investigating (see section 7) before
trusting ASSD numbers from either winning model.

Total parameters: 100,622,065 (PhysicsAwareAdapter) / 100,730,416 (Plain
LoRA) / 101,985,328 (Spacing-Conditioned LoRA — the per-layer spacing FiLM
networks add ~1.25M params over Plain LoRA). An earlier implementation of
Spacing-Conditioned LoRA scaled the FiLM network's hidden size with the
attention layer's width, which for qkv layers (2304-dim) alone added ~31M
trainable params (31.79% of the model) — caught and fixed *before* training,
by checking the actual parameter count rather than assuming the design was
fine (see `models/spacing_lora.py`'s comments) — to a fixed small hidden
size (16), landing at the 8.88% reported above.

### 5.3 Resolution-OOD test (the most important experiment in this project) — REVERSES section 5.2's ranking

All three trained models (section 5.2) evaluated on `kidney_1_voi` — the
5.2μm specimen, **held out from all training** by `train_real_gt.py`/
`train_plain_lora.py`/`train_spacing_lora.py`'s default `exclude_for_ood`
(see section 2.1). Training data was exclusively ~50μm; this is a genuine
~10x unseen resolution shift, not synthetic. 40 patches sampled, 34-35
excluded as empty-target (this specimen's vasculature is sparser than the
50μm training kidneys — mean FG fraction 0.14-3.56% vs. training's 0.25-0.73%).

| Model | In-dist. Dice (50μm) | **OOD Dice (5.2μm)** | OOD IoU | OOD clDice | OOD HD95 | OOD ASSD |
|---|---|---|---|---|---|---|
| PhysicsAwareAdapter | 0.157 | 0.064 | 0.035 | 0.059 | 53.1 | 25.3 |
| Plain LoRA | 0.067 | **0.067** | **0.036** | 0.210 | 50.7 | 25.9 |
| Spacing-Conditioned LoRA | **0.206** | 0.002 | 0.001 | 0.008 | 41.6 | **18.7** |

**This reverses section 5.2's ranking and is reported exactly as measured —
no cherry-picking, no reframing to save the hypothesis.** Spacing-Conditioned
LoRA, the clear in-distribution winner, **collapses to near-zero Dice (0.002)**
on the unseen resolution — the worst of the three models on Dice/IoU/clDice,
despite having the best HD95/ASSD (a model that predicts almost nothing can
still score well on boundary distance if the few pixels it does predict are
in roughly the right place — this is a real, known way these metrics can
mislead when Dice is this low, not a contradiction).

**Initial hypothesis, tested directly and REFUTED — reported honestly rather
than left standing:** the first guess was that the spacing-FiLM network
(trained on a narrow range, effectively a single spacing ~50μm across all 4
training kidneys) would extrapolate badly ~10x out-of-range and produce
large/erratic gamma/beta at 5.2μm, corrupting the LoRA branch. Checked
directly by computing `spacing_film(spacing)` at both values on the trained
model: at 50μm, gamma∈[0.70, 1.54] (mean 1.05); at 5.2μm, gamma∈[0.97, 1.06]
(mean 1.01) — the OOD modulation is actually *smaller and tamer* (closer to
a no-op identity) than the in-distribution one, the opposite of the
hypothesis. **The FiLM network is not the confirmed cause of the collapse —
the real cause is still an open question.**

A more plausible remaining explanation, partially checked: a 64³ patch at
5.2μm covers a physical region ~10x *smaller* than the same patch at 50μm
(≈333μm vs. ≈3200μm across) — the model is looking at a much more tightly
zoomed-in field of view than anything in training, a raw visual domain shift
independent of the spacing *value* fed to the FiLM network. Direct evidence
for this: target foreground fraction is ~20x higher on average at 5.2μm
(mean 0.67%, up to 6.7% per patch, n=10 patches) than at 50μm (mean 0.032%,
up to 0.67%, n=10 patches) — consistent with the same real vessel occupying
proportionally far more of a much-smaller physical window. z-score
normalization itself was checked and is not the issue (both resolutions
normalize to mean≈0, std≈0.90-0.98).

This does NOT, however, come from an obvious numerical fault in the frozen
backbone: the image_encoder's raw output statistics are nearly identical
between resolutions (50μm: mean=0.0013, std=0.218; 5.2μm: mean=0.0014,
std=0.221; similar min/max) — ruling out a gross activation blowup or
degenerate output. The likely remaining issue is therefore about *content*,
not magnitude: the frozen encoder (and the LoRA weights trained only on
50μm patches, deep inside it) may simply have learned to recognize visual
patterns at the wrong physical scale for a 10x-zoomed-in view, something
same-mean/std statistics cannot detect or rule out — this would need a
deeper per-channel/spatial analysis to confirm, not yet done. This could
plausibly hit Spacing-Conditioned LoRA hardest if its encoder-internal LoRA
weights are more scale-specific than PhysicsAwareAdapter's later, coarser
adaptation point or Plain LoRA's (unmodulated but also 50μm-only-trained)
weights — but this remains an open, untested hypothesis, not a conclusion.

**This finding is more scientifically important than section 5.2's positive
result**, and directly changes what this project can currently claim: the
proposed method is NOT yet shown to generalize across resolutions — if
anything, current evidence suggests it generalizes *worse* than the simpler
Plain LoRA baseline on real out-of-distribution data. Next steps (not yet
done): identify the actual cause (compare patch field-of-view / visual
statistics at 50μm vs 5.2μm directly), train on a wider range of real
spacings if more resolutions can be added, and re-run this OOD test after
that investigation rather than trusting the current single-checkpoint result.

### 5.4 Controlled 100-epoch GPU retrain — CONFIRMS section 5.3, not an under-training artifact

Section 5.2/5.3's numbers came from a 10-epoch CPU run. The open question
those results left was whether the OOD collapse was real or just an
artifact of too little training. This retrain (100 epochs, both
architectures, real GPU, same data split, same protocol — see section 3.4
in test.sh for the full bug history of getting this kernel running)
answers that directly. Literal printed output of `evaluate_real_gt.py` from
Kaggle kernel version 7 (`rabeya100x/hip-vesseladapt-100ep-gpu-train`),
fetched via `kaggle kernels_logs` after the kernel reached `COMPLETE`:

| Model | Trainable | In-dist Dice | In-dist IoU | In-dist clDice | OOD Dice | OOD IoU | OOD clDice |
|---|---|---|---|---|---|---|---|
| Plain LoRA (100 ep, GPU) | 7.75% | 0.1838 (n=26/100) | 0.1201 | 0.2466 | 0.1672 (n=5/40) | 0.1008 | 0.1575 |
| Spacing-Conditioned LoRA (100 ep, GPU) | 8.88% | **0.3145** (n=18/100) | **0.2279** | **0.3268** | **0.0058** (n=5/40) | 0.0029 | 0.0162 |

**The pattern from section 5.2/5.3 is confirmed, not resolved by more
training — if anything it sharpens:**
- In-distribution, Spacing-Conditioned LoRA's lead over Plain LoRA *widened*
  going from 10→100 epochs (0.206 vs 0.067 at 10 epochs → 0.3145 vs 0.1838
  at 100 epochs).
- Out-of-distribution, Spacing-Conditioned LoRA is still the worst of the
  two by more than an order of magnitude (0.0058 vs Plain LoRA's 0.1672),
  and is still far below its own in-distribution score (0.0058 vs 0.3145 —
  a ~98% relative drop). Plain LoRA's OOD score (0.1672), by contrast, sits
  close to its own in-distribution score (0.1838) — it degrades gracefully;
  Spacing-Conditioned LoRA collapses.
- This rules out "10 epochs was too few" as the explanation for section
  5.3's finding. The collapse is a real property of the trained model, not
  an artifact of under-training — this is the honest, load-bearing
  conclusion the whole OOD root-cause investigation (evaluate_fov_confound.py,
  analyze_film_layers.py, run_ablation.py — all written, see section 7) now
  needs to explain, run against these actual 100-epoch checkpoints rather
  than the earlier 10-epoch ones.

**Caveat, stated honestly:** only 5 of 40 sampled OOD patches contained any
annotated vessel at all, for *both* models — the OOD Dice/IoU/clDice above
are each averaged over just 5 patches. The gap (0.1672 vs 0.0058) is large
enough to be suggestive even at this n, but a properly powered OOD sample
size is still on the to-do list (section 7).

**Two things noticed while reading this run's raw output, reported as
found rather than smoothed over:**
- **Training loss converged to nearly the same value for both models**
  (Plain LoRA 1.4737, Spacing-Conditioned LoRA 1.4900, both epoch 100/100)
  — unlike the 10-epoch run, where Spacing-Conditioned LoRA's loss was
  visibly lower (1.56 vs Plain LoRA's 2.05). At 100 epochs, final training
  loss no longer predicts the large gap in real-GT Dice between the two
  models — evaluation-time metrics and training loss are measuring
  different things here, and only the former should be trusted for the
  comparison.
- **HD95 and ASSD came back as `nan` (n=0) for all four evaluations in this
  run** (both models, both in-dist and OOD) — different from the earlier
  CPU run, which produced real HD95 values and only ASSD as `inf` for two
  of the three architectures. `evaluate_real_gt.py`'s `_safe_metric()`
  silently caught whatever exception MONAI's `HausdorffDistanceMetric`/
  `SurfaceDistanceMetric` raised on every single non-empty-target patch;
  Dice/IoU/clDice succeeded on the exact same GPU tensors in the same loop
  iteration, so this isn't a device-transfer problem with the tensors
  themselves. Fixed `_safe_metric()` to print the real exception the first
  time each metric type fails, instead of only ever returning a bare
  `None` — the next run against these checkpoints will show the actual
  cause instead of leaving it a mystery. Not yet diagnosed as of this
  writing.

### 5.5 Field-of-view confound test — RUN FOR REAL, substantial support for the FOV hypothesis

The 100-epoch checkpoints were downloaded from the Kaggle kernel's output
(the two `best_model_*.pth` files, via signed URLs — not the full working
directory) and `evaluate_fov_confound.py` run against both, locally, with
`samples=40`. Recall the method: instead of a native-scale 64³ crop of
kidney_1_voi (5.2μm), extract a much larger cube (sized so its *physical*
extent matches a 64³ patch at the training spacing, ~50μm) and downsample
it to 64³ before evaluating — same real 5.2μm data, matched field of view.

| Model | In-dist (5.2) | OOD, native-scale crop (5.3) | OOD, FOV-matched (this test) |
|---|---|---|---|
| Plain LoRA | 0.1838 (n=26/100) | 0.1672 (n=5/40) | **0.2895** (n=40/40) |
| Spacing-Conditioned LoRA | 0.3145 (n=18/100) | **0.0058** (n=5/40) | **0.2215** (n=40/40) |

**This is substantial, not marginal, support for the field-of-view
hypothesis.** Two things stand out:
- Every single one of the 40 FOV-matched patches contained real vessel
  (0 empty), versus 35/40 *empty* in the native-scale OOD crop. The
  native-scale 64³ window at 5.2μm covers too little real tissue to reliably
  contain a vessel at all — a big part of why that evaluation only had 5
  usable patches in the first place.
- Spacing-Conditioned LoRA's OOD Dice recovers from catastrophic (0.0058,
  a ~98% drop from its own in-distribution score) to 0.2215 — about 70% of
  its in-distribution performance — just by giving it a matching field of
  view on the *same* real OOD data. Plain LoRA also improves substantially
  (0.1672 → 0.2895), so field of view is not the *whole* story (Plain LoRA
  was never "collapsed" to begin with), but it is clearly a major
  contributor for both models, and the dominant one for
  Spacing-Conditioned LoRA specifically.
- Under FOV-matched conditions, Plain LoRA edges out Spacing-Conditioned
  LoRA — the in-distribution ranking (section 5.4) reverses again once the
  confound is controlled for. **Confirmed significant**, not just an n=40
  eyeball comparison: a fresh scoring pass (`significance_test_fov.py`,
  40 fresh patches per model — exact means differ slightly from the numbers
  above since `evaluate_fov_confound.py` samples a new random cube each
  call, but the direction and magnitude are consistent: Plain LoRA 0.3681
  vs Spacing-Conditioned LoRA 0.2618) gives a Mann-Whitney U test p=0.0216,
  significant at α=0.05. The gap is real, not sampling noise.

**Interpretation, stated as a hypothesis, not a proven conclusion:** most
(not all) of section 5.3/5.4's "OOD collapse" looks like an ordinary
never-seen-visual-scale domain shift, not something specific to how
Spacing-Conditioned LoRA's FiLM mechanism uses the numeric spacing value.
The per-layer FiLM breakdown below adds a second, complementary piece of
evidence for *why* Spacing-Conditioned LoRA is hit harder than Plain LoRA
by whatever FOV-shift remains even after this correction.

### 5.6 Per-layer FiLM breakdown — RUN FOR REAL, a second lead beyond the FOV effect

`analyze_film_layers.py` run against the real 100-epoch
Spacing-Conditioned LoRA checkpoint, comparing each of the 24 injected
layers' gamma/beta output at the in-distribution spacing (50μm) vs. the OOD
spacing (5.2μm) — no forward pass through the image encoder needed, since
`spacing_film` is a small MLP over the 3-number spacing input alone.

The earlier aggregate check (section 5.3, 10-epoch checkpoint) refuted
"FiLM extrapolates to wild/erratic values at unseen spacing" — OOD gamma
was, if anything, tamer than in-distribution. At 100 epochs, the per-layer
breakdown shows the same direction but **far more pronounced**: gamma
values at the *in-distribution* spacing have grown large during training
(e.g. layer 19: gamma_mean=6.52, gamma_max=21.6 at 50μm; layer 2:
gamma_max=19.7 at 50μm), while the same layers' gamma at the *OOD* spacing
stays close to identity (layer 19: gamma_mean=1.59, gamma_max=3.23 at
5.2μm; layer 2: gamma_max=3.06 at 5.2μm) — a pattern that holds broadly
across all 24 layers, not just one outlier.

**Revised hypothesis, worth testing further:** rather than FiLM
extrapolating to *dangerous* values OOD, training seems to have pushed the
FiLM network toward large, aggressive modulation specifically *tuned to*
the training spacing — at 100 epochs the model may have become reliant on
that strong modulation to segment 50μm data well. At an unseen spacing, the
FiLM output reverts toward a near-identity no-op (gamma≈1, beta≈0),
effectively falling back to something close to Plain LoRA's behavior *for
that layer* — but not exactly Plain LoRA, since the underlying LoRA
A/B weights themselves were trained jointly with this strong modulation
active, not independently. Combined with section 5.5's finding, the
current best-supported picture is: most of the OOD failure is an ordinary
field-of-view domain shift, and Spacing-Conditioned LoRA's FiLM mechanism
compounds it by degenerating toward (but not cleanly reaching) a
plain-LoRA-like behavior it was never actually optimized for. Still a
hypothesis, not confirmed — the natural next check is training Plain LoRA
and Spacing-Conditioned LoRA on a wider range of real spacings so "unseen
spacing" is no longer confounded with "unseen field of view" at all.

### 5.7 Ablation: clDice loss term, 100 epochs GPU — RUN FOR REAL

`run_ablation.py`'s 4th stage (Spacing-Conditioned LoRA with the clDice
loss term turned off, via the new `use_cldice=False` flag on
`HiPVesselLoss`) trained separately on Kaggle GPU, 100 epochs, identical
protocol to section 5.4 otherwise.

| Model | In-dist Dice | In-dist clDice | OOD Dice | OOD clDice |
|---|---|---|---|---|
| Spacing-Conditioned LoRA, WITH clDice (5.4) | 0.3145 (n=18/100) | 0.3268 | 0.0058 (n=5/40) | 0.0162 |
| Spacing-Conditioned LoRA, NO clDice | **0.1898** (n=19/100) | 0.1927 | 0.0015 (n=3/40) | 0.0035 |

**The clDice loss term contributes real in-distribution performance** —
removing it drops in-distribution Dice by about 40% relative (0.3145 →
0.1898), not just the clDice metric itself (which would be an unsurprising
mechanical effect of removing a term that's directly optimizing something
close to it) but Dice too, a metric the loss doesn't directly optimize.
**It does not explain the OOD collapse** — OOD Dice is catastrophically
low either way (0.0058 vs 0.0015), both near the noise floor at n=3–5. The
clDice ablation and the FOV/FiLM findings (sections 5.5, 5.6) are
independent, non-competing explanations: clDice loss helps in-distribution
segmentation quality generally; the OOD collapse looks driven mostly by
field-of-view mismatch and FiLM's spacing-specific modulation, not by
clDice one way or the other.

### 5.8 Root cause found: HD95/ASSD `nan` on Kaggle GPU (sections 5.4, 5.7)

The improved `_safe_metric()` logging (section 5.4) finally surfaced the
real exception on this ablation run, and it's an environment problem, not
a bug in this project's code:

```
HausdorffDistanceMetric raised: .../cupy/_core/include/cupy/_cccl/thrust/
thrust/detail/config/cpp_dialect.h(74): catastrophic error: #error
directive: Thrust requires at least C++17.
```

MONAI's `HausdorffDistanceMetric`/`SurfaceDistanceMetric` route GPU tensors
through a CuPy-JIT-compiled CUDA kernel for the distance transform; on
Kaggle's kernel image, that JIT compilation itself fails outright (a
CuPy/Thrust/CUDA-toolkit version mismatch in Kaggle's Docker image, nothing
this project controls). Dice/IoU/clDice never go through this code path, so
they were unaffected — which is exactly why only HD95/ASSD were `nan`
while everything else computed normally. Fixed in `evaluate_real_gt.py` by
moving `binary_pred`/`targets` to CPU specifically for the HD95/ASSD calls
(`.cpu()` right before `_safe_metric()`), sidestepping the broken GPU/CuPy
path entirely rather than depending on Kaggle's toolchain being fixed.
Verified locally (still produces real HD95/ASSD values, no regression) —
not yet re-verified on Kaggle GPU, since re-running either 100-epoch
kernel just to check this would cost real GPU quota for an already
reasonably-confident fix.

## 6. Known limitations (stated honestly, not hidden)

- **Absolute DSC is low (0.06–0.08).** Two likely causes, both real: (a) very
  limited training so far (20 epochs × 24 patches/epoch = 480 gradient steps
  total, on a CPU-only machine — each additional epoch costs real wall-clock
  hours); (b) the Frangi pseudo-labels are themselves a noisy, heuristic
  target — visually confirmed to be sparse, sometimes fragmented blobs rather
  than a clean connected vessel tree, not a bug but a ceiling on label quality
  without further denoising work or real expert annotation.
- **Epoch-to-epoch DSC is noisy**, not monotonically improving (e.g. Heart:
  0.077 at 10ep → 0.043 at 18ep → 0.060 at 20ep). With only 5 evaluation
  patches per organ, individual DSC estimates have high variance; the zero-shot
  vs. fine-tuned *comparison* is the more reliable signal than any single
  absolute number.
- **Betti-number gaps for Lung/Kidney are large**, but likely partly reflect
  pseudo-label fragmentation (the target itself has many spurious components)
  rather than the model being topologically wrong — needs a cleaner reference
  to disentangle.
- **`CollapseDetectionHead` exists but is untrained/unvalidated** — it runs
  (multi-task output alongside the mask), but no supervision signal or
  evaluation has been built for it yet.
- **`clDice` topological loss** is wired in (`losses/combined_loss.py`) but its
  individual contribution hasn't been ablated separately from Dice/BCE.
